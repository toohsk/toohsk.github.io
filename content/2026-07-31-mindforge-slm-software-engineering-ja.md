Title: MindForge：小型言語モデルにゼロからのプログラム全ライフサイクル開発を教える
Date: 2026-07-31
Category: AI/ML
Tags: SLM, AI, 論文解説
Summary: MindForgeはオープンソースのコマンドラインプログラムをソースコード非公開の訓練環境に変換するパイプラインで、教師エージェントのプログラム開発全工程トラジェクトリを用いてQwen3.6-27BのProgramBenchスコアを37.98%から49.51%に向上させ、2〜3倍大きなフロンティアモデルに匹敵する性能を実現した。

## なぜこの研究が重要か

AIにとって最も難しいソフトウェアエンジニアリングタスクは既存コードのバグ修正ではない——**ゼロからの完全なプログラム構築**だ。ドキュメントとコンパイル済みバイナリのみを与えられたエージェントは、完全な仕様の推論、アーキテクチャ設計、実装、デバッグ、テスト作成、動作するビルドの提出という全工程を遂行しなければならない。

最も優秀なフロンティアモデルでさえ、これに壊滅的に失敗する。ゼロからのプログラム構築ベンチマークProgramBenchでは、GPT-5.5でさえタスクの1%未満しか解決できない。これはベンチマーク較正の問題ではなく、本物の能力ギャップだ。

原因は構造的だ。既存のコーディングエージェントの訓練パイプラインは既存のコードベースを前提としている——バグ修正（障害を注入してモデルに修正させる）、機能実装（既存コードを受け取り関数を追加する）、リポジトリレベルタスク（ナビゲート、理解、編集）。**これらはどれも完全な開発ライフサイクルを教えない。** バグ修正に最適化されたエージェントは仕様を推論することを学ばない。コード補完で訓練されたエージェントはゼロからアーキテクチャを設計することを学ばない。

MindForgeはソースコードへのアクセスがない訓練環境——コンパイル済みバイナリとドキュメントのみ——を構築し、エージェントが仕様探索から動作するビルドまでのソフトウェア開発プロセス全体を完了しなければならない設定でこれに対処する。

結果：Qwen3.6-27Bを1,001個のそのようなトラジェクトリでファインチューニングすると、ProgramBenchスコアが37.98%から49.51%に向上し、DeepSeek V4 Pro（47.80%）を上回り、2〜3倍大きなOpus 4.7（51.38%）に迫った。

## 技術的なアプローチ

MindForgeは2つのフェーズで動作する：環境構築とトラジェクトリ収集。

### フェーズ1：ソースフリー環境の構築

パイプラインはオープンソースのコマンドラインプログラムを制御された訓練環境に変換する：

**1. リポジトリ選択。** リポジトリを特定のコミットに固定し、自己完結性（インターネットアクセス不要、資格情報不要、特殊ハードウェア不要）をスクリーニングし、ProgramBenchのテストインスタンスと重複しないことを確認する。

**2. オフラインスクリーニング。** エクスプローラーエージェントがソースコードとドキュメントを読み、プログラムの動作がドキュメントとバイナリ動作から明確に識別できるかどうかを判断する。曖昧なプログラムはコストのかかるビルド作業が始まる前に棄却される。

**3. ビルド発見。** ビルダーエージェントがクリーンなリポジトリチェックアウトからプログラムをコンパイルする自己完結型のビルドスクリプトを生成する。スクリプトは決定論的でなければならない——状態なしで再現可能。

**4. 動作等価チェック。** ビルドスクリプトが新鮮なサンドボックスで再実行される。元のバイナリと再構築されたバイナリの両方が同じ動作チェック（サンプル入力を持つコマンド呼び出し）に対してテストされる。同一の終了コード、stdout、stderrが要求される。これにより不安定なビルドをフィルタリングする。

**5. ソースフリー検証。** コンパイル済み実行ファイルがソースコードの読み取り可能な形式のスキャンを受ける。元の実装を明らかにするパス、シンボル名、その他のマーカーは再ビルドを引き起こす。ソースの漏洩がない実行ファイルのみが通過する。

受け入れられた環境は、コンパイル済みの参照実行ファイルと公開ドキュメントのみを含むDockerイメージを生成する。**訓練エージェントはどの段階でもソースコードを見ない。**

### フェーズ2：トラジェクトリ収集と改良

**収集：** GLM-5.2（教師エージェント）がmini-swe-agentをスキャフォールドとしてクリーンルームDockerイメージ内で動作する。教師はバイナリとドキュメントのみを受け取り、独立して仕様を引き出し、アーキテクチャを設計し、実装し、デバッグし、動作するビルドを提出しなければならない。

**トラジェクトリ分析：** 収集されたトラジェクトリは複数のソフトウェア開発段階をカバーする：
- 仕様探索：トラジェクトリの99.1%
- アーキテクチャ設計：87.1%
- バグ特定：59.4%
- 改良：64.0%

この多段階カバレッジが、既存のコーディングエージェントデータセットが欠いている重要な訓練シグナルだ。

**2つの改良手順：**

**1. インフラストラクチャノイズリカバリー。** 長期的なトラジェクトリ（200〜800+ターン）は過渡的なインフラストラクチャ障害（APIエラー、サービス中断）に頻繁に遭遇する。これらを破棄する代わりに、パイプラインは最後の正常状態まで巻き戻し、クリーンな環境ですべての前の呼び出しを再生し、再開する。

**2. 推論書き換えメカニズム。** 教師がツール呼び出しエラーを起こして誤ったターンが削除されると、後続のターンが今や削除されたエラーを参照する推論を含む可能性がある。修復モデル（GLM-5.2）が影響を受ける推論コンテンツのみを書き換える——ツール呼び出しや環境レスポンスには触れない——トラジェクトリの一貫性を回復する。すべての書き換えは受け入れ前に安全チェックを受ける。

### 訓練

ファインチューニング：Qwen3.6-27Bを1,001個の全ライフサイクルトラジェクトリで訓練。学生は分離されたコード編集ではなく、教師のエンドツーエンドの開発プロセスを再現することを学ぶ。

## 先行研究との比較

**ProgramBenchのパフォーマンス：**

| モデル | ProgramBenchスコア |
|--------|-------------------|
| Qwen3.6-27B（ベース） | 37.98% |
| DeepSeek V4 Pro | 47.80% |
| **MindForge-27B** | **49.51%** |
| GLM-5.1 | 50.9% |
| Opus 4.7 | 51.38% |

**7つのベンチマークでの汎化：**

| ベンチマーク | 改善 |
|-------------|------|
| RepoZero-C2Rust | +31.00% |
| DeepSWE | +14.16% |
| NL2Repo-Bench（テストあり） | +10.70% |
| NL2Repo-Bench（テストなし） | +4.56% |
| SWE-bench Verified | +5.04% |
| SWE-bench Pro | +5.93% |
| SWE-bench Multilingual | +5.22% |
| FeatBench | +4.94% |

改善はProgramBenchに特化したものではなく、バグ修正、機能実装、リポジトリ生成、言語間変換など、全く異なるタスクにわたる7つの分布外ベンチマークに汎化する。

## 実験結果の読み方

**ProgramBenchの37.98% → 49.51%のジャンプ**は、ベースモデルとフロンティアLLMの間のギャップの約3分の1を閉じる。注目すべきは、ファインチューニングされたモデルがより小さいにもかかわらずDeepSeek V4 Proを上回り、大幅に大きなOpus 4.7とGLM-5.1に迫ることだ。

**RepoZero-C2Rustの改善（+31.00%）**が最も劇的な単一ベンチマーク結果だ。RepoZeroはCのソース説明からRustで完全なリポジトリレベルのコードを生成することを要求する——アーキテクチャ思考と言語間専門知識の両方を必要とするタスク。

**コマンド失敗率分析**は行動変化の定性的な証拠を提供する。MindForge-27Bのアクション分布は教師に大幅に近づき、重要なことに、そのコマンド失敗率はベースモデルより*低い*——はるかに長いトラジェクトリ（830ターン、848ツール呼び出し、2億950万トークンの実行を含む）にもかかわらず。

**1,001個の訓練トラジェクトリ。** データ効率が注目に値する。わずか1,001個の全ライフサイクルトラジェクトリがはるかに大きなモデルを上回る性能を実現する。これは訓練シグナルの*品質*（分離されたパッチとは対照的な完全な開発サイクル）が量よりも重要である可能性を示唆する。

## アルゴリズムの重要部分の解説

### ソースフリー環境が訓練パラダイムをシフトさせる理由

従来のコーディングエージェントの訓練パラダイム：ソースコードを提供し、モデルに修正させる。MindForgeはこれを逆転させる：バイナリとドキュメントのみを提供し、モデルにソースを構築させる。

この逆転により、モデルは**仕様推論**能力を開発することが強制される。ソースアクセスなしで、モデルは：
1. ドキュメントを注意深く読んで意図された動作を理解する
2. テスト入力でバイナリをプローブしてエッジケースを発見する
3. 実装要件についての仮説を形成する
4. さらなるプローブを通じてそれらの仮説を検証する

これらの能力は、仕様が不完全、曖昧、または実際の動作と矛盾している現実のソフトウェアエンジニアリングシナリオに転移する。

### 動作等価チェックが品質ゲートとして機能する理由

動作等価チェック（新鮮なサンドボックスでビルドスクリプトを2回実行して出力を比較する）は非自明なエンジニアリング貢献だ。その目的：

- 環境が決定論的であることを保証する（どのマシンでも再現可能）
- 非決定論的プログラム（タイミング、乱数シード、環境状態に依存する出力を持つ）をフィルタリングする
- エージェントが評価中に一貫して動作しない環境を解くことを学ぶのを防ぐ

このチェックなしでは、訓練分布には「ファジー」な環境——正しい動作が曖昧な——が含まれ、訓練シグナルを汚染する。

### インフラストラクチャノイズリカバリーが隠れた乗数として機能する

長期的なトラジェクトリ（200〜800+ターン）は生成に費用がかかる。APIタイムアウトによってターン600で中止された単一のトラジェクトリは、大きな無駄な推論コストを表す。インフラストラクチャノイズリカバリーメカニズム——最後の正常状態まで巻き戻してクリーンな環境で再開——は簡潔に説明されているが、実用上の重要なエンジニアリング貢献を表す。

### 推論書き換えが因果的整合性を保つ理由

推論書き換えメカニズムの重要な制約：ツール呼び出しや環境レスポンスは決して変更しない。推論コンテンツ（アクション間のモデルの内部独り言）のみが編集可能だ。

これはトラジェクトリの因果的整合性を保持する：実際に取られたアクションとその結果はグランドトゥルースのまま。それらのアクションをつなぐ推論のみが滑らかにされる。これにより学生は観察されたツール結果と矛盾した方法で推論することを学ぶのではなく、観察された結果について正しく推論することを学ぶ。

## 限界と課題

1. **27Bは多くの定義では「小型」ではない。** フロンティアシステム（100B+）に対するQwen3.6-27Bの「小型モデル」としての位置付けは相対的だ。オンデバイス展開では、27Bはほとんどのハードウェアには実用的ではない。

2. **コンパイル済みのコマンドラインプログラムのみ。** パイプラインは決定論的なバイナリ出力を生成するプログラム向けに設計されている。GUI、ネットワークアプリケーション、ステートフルプログラムは除外される。

3. **6つのコンパイル言語のみ。** 562個の環境は6つのコンパイル言語のみをカバーする。スクリプト言語（Python、JavaScript）やドメイン固有言語のカバレッジはない。

4. **教師依存の品質上限。** トラジェクトリの品質は教師エージェントの能力に依存する。GLM-5.2が特定の問題タイプで系統的なエラーを起こすと、それらは学生に学習される。

## 今後の展望

**著者の示唆：**
- GUIやネットワークアプリケーションへの環境拡張
- スクリプト言語（Python、JavaScript）への拡張
- 強化学習ベースのトラジェクトリ改善の探索

**この研究から派生する有望な研究方向：**

1. **より小さな学生のための圧縮トラジェクトリ蒸留。** 現在のアプローチは27Bモデルをファインチューニングする。7Bや1Bモデルへの拡張には、より短いトラジェクトリか、より効率的な訓練が必要だ。トラジェクトリ圧縮（探索フェーズの要約）がこれを可能にするかもしれない。

2. **反復的自己改善。** ファインチューニングされたMindForge-27Bが次の訓練ラウンドのためのより良い教師として機能できる。各世代のモデルが次の世代のより高品質なトラジェクトリを生成する自己改善ループを作る。

3. **独立能力としての仕様推論。** 仕様探索フェーズ（トラジェクトリの99.1%）を抽出して独立した能力として訓練できる。バイナリからの仕様推論のみで訓練されたモデルはリバースエンジニアリング、ドキュメント生成、セキュリティ分析をサポートできる。

4. **他のエージェント的ドメインへのソースフリー訓練の汎化。** 観察可能な動作のみを提供し、ソース構造は提供しないパラダイムはコード以外にも一般化する。ロボット操作タスク（センサー読み取りで観察可能な動作）、ウェブナビゲーション（DOM状態で観察可能な動作）、科学的分析（実験結果で観察可能な動作）が全てソースフリー訓練環境としてフレーム化できる。

5. **多言語翻訳トラジェクトリ。** RepoZero-C2Rustが+31.00%の改善を示した。言語の境界を越えるトラジェクトリ（ある言語で実装し、別の言語のバイナリに対して検証する）を意図的に含めることで、言語間汎化をさらに強化できる。

## エッジ・オンデバイスへの示唆

MindForgeの直接的な展開示唆は27Bパラメータスケールによって制限される——現在のスマートフォンやエッジデバイスは27Bモデルを効率的に実行できない。しかし研究貢献はエッジAIへの重要な間接的示唆を持つ。

**より良いコーディングエージェントがより良いオンデバイスツールを構築できる。** MindForgeで訓練された27Bモデルがほぼフロンティアレベルの能力でゼロからのプログラムを構築できるなら、エッジハードウェア向けに最適化された軽量なアルゴリズム実装の開発を支援できる——SIMDに最適化されたルーティン、ハードウェア固有の推論カーネル、メモリ効率の良いデータ構造。

**パイプラインはより小さな学生に一般化できる。** MindForgeパイプラインのどの部分も27Bの学生を必要としない。同じソースフリー環境と教師トラジェクトリを7Bや3Bモデルのファインチューニングに使用できる。精度向上は小さくなるかもしれないが、パラダイムはスケール非依存だ。

**組み込みシステムのための仕様推論。** バイナリとドキュメントからプログラムの動作を推論することを学ぶ仕様探索能力は、バイナリのみのSDKや文書化が不十分な動作を持つハードウェアコンポーネントとのインターフェースが必要な組み込みシステムエンジニアリングに直接関連している。

**ドメイン固有SLMのための訓練データ生成。** 高度に制約されたドメイン（Cでのリアルタイム組み込みシステム、アセンブリでのファームウェア）の場合、MindForgeパイプラインは専門的な訓練データを生成できる。組み込みプログラミング用のドメイン固有SLM——ハードウェアに近接したプログラムから生成されたトラジェクトリで訓練された小型モデル——が長期的な応用となる。
