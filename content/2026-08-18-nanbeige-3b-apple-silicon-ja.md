Title: Nanbeige4.2-3B on Apple Silicon: SLMのオンデバイスデプロイで直面する5つのバグと解決策
Date: 2026-08-18
Category: AI/ML
Tags: SLM, AI, 論文解説
Summary: LoopedTransformerアーキテクチャを採用した3B SLMのApple Silicon上での展開で発見された5つのクリティカルバグと、チャンク化プリフィルによるメモリ2.7倍拡張を含む解決策を体系的に報告した実践的研究。

## なぜこの研究が重要か

SLM（Small Language Model）の研究は急速に進んでいるが、**「論文上の性能」と「実際にデバイスで動くか」のギャップ**は依然として大きな問題だ。

Nanbeige4.2-3Bは最近リリースされたエージェンティックタスク特化の3B SLMで、Qwen3.5-4BやQwen3.5-9Bを超えるとされるオフィスワークフロー性能を報告していた。しかし実際にApple Silicon（M2 Max）上で動かそうとすると、**5つの独立したバグにより完全に動作不能**であった。

この研究は学術的な性能向上ではなく、**実用化の最後の1マイル**に焦点を当てる。なぜSLMが「使える状態」でリリースされないのか、どのようなバグが潜んでいるのか、そしてLooped Transformer（LT）アーキテクチャが持つ固有のメモリ問題をどう解決するか——これらをApple Silicon上で徹底的に検証した実践的報告だ。

**なぜこの研究が広く重要か？**
1. Apple Silicon（M-series MacBook/Mac Studio）はエッジAI推論の主要プラットフォームの一つ
2. Looped Transformerアーキテクチャはパラメータ効率の高いSLM設計として注目されている
3. ここで発見されたバグは、同類のアーキテクチャを持つ他モデルでも発生しうる

## 技術的なアプローチ

### Looped Transformerアーキテクチャとその特性

Nanbeige4.2-3BはLooped Transformer（LT）アーキテクチャを採用している。

**通常のTransformer**: 
```
入力 → Layer1 → Layer2 → ... → LayerL → 出力
```

**Looped Transformer**:
```
入力 → [Layer1 → Layer2 → ... → LayerL] → [Layer1 → Layer2 → ... → LayerL] → 出力
       ←−−−−−−−−−−− 1回目のパス −−−−−−−−−−−→  ←−−−−−−−−−−− 2回目のパス −−−−−−−−−−−→
             （重みは両パスで共有）
```

同じL個のレイヤーを2回通すことで、**実効的な深さを2倍にしながらパラメータ数は変えない**。LT論文はこれにより固定パラメータ予算で大きなモデルを超えることを示した。

**メモリへの影響**: セルフアテンションのプリフィル時のピークアクティベーションメモリは、各ループパスでO(prompt_len²)が発生する：
- 通常Transformer: O(L × prompt_len²)
- Looped Transformer: O(2L × prompt_len²) — **2倍のメモリ要求**

32 GiB統合メモリ（OS、他プロセス、モデルで共有、CUDAのようなページアウトなし）では、長いコンテキストで壊滅的になる。

### 発見された5つのバグ

| # | バグ | 症状 | 深刻度 |
|---|------|------|--------|
| 1 | **RoPEバッファの永続化** | inv_freqバッファがロード時にゼロ初期化、位置情報なしで推論 | 最重要（サイレントに誤動作） |
| 2 | **RoPE-config dispatchのKeyError** | 有効なconfig値でモデルロードが失敗 | デバイス非依存クラッシュ |
| 3 | **Cache APIのセンチネル不一致** | 削除済みAPIへの呼び出しでクラッシュ | 推論時クラッシュ |
| 4 | **Position-IDs再トリミング** | MPSデバイスでのみハードクラッシュ | MPS固有クラッシュ |
| 5 | **Tied-weightsキー形式** | save_pretrainedに失敗 | 再シリアライズ不可 |

**バグ1（RoPEバッファの永続化）が最も危険**。モデルはクラッシュせず「流暢に見えるが位置的に非一貫な出力」を生成する。デバッグなしでは「性能が悪い」と誤認識する可能性がある。

RoPE（Rotary Position Embedding）は各トークンの位置情報をアテンション計算に組み込む機構で、inv_freqバッファがゼロだと全トークンが「位置0」として扱われる。

### チャンク化プリフィル（Chunked Prefilling）による解決

LTのメモリ問題を解決するため、著者らは**チャンク化プリフィル（CP）**を導入：

```python
# 通常のナイーブプリフィル（全プロンプトを一括処理）
# output = model(input_ids=full_prompt)  # O(prompt_len²) per loop × 2 loops

# チャンク化プリフィル（256トークン単位で処理）
cache = DynamicCache()
n_full_chunks = (total_len - 1) // chunk_size  # chunk_size=256

for i in range(n_full_chunks):
    start, end = i * chunk_size, (i+1) * chunk_size
    outputs = model(
        input_ids=input_ids[:, start:end],
        past_key_values=cache,
        use_cache=True,
        cache_position=torch.arange(start, end),
    )
    cache = outputs.past_key_values

# 残りトークンを通常の生成で処理
return model.generate(input_ids=remaining, past_key_values=cache, ...)
```

**メモリ計算量の変化**：
- ナイーブ: O(prompt_len²) per loop iteration = 全プロンプト長の二乗に比例
- チャンク化: O(chunk_size × running_total) = チャンクサイズ × 累積KV長に比例（ピーク抑制）

### システムプロンプトの退行バグ

LTメモリ問題とは独立して、チャットテンプレートに重大な欠陥があった：

```
caller-supplied system message あり: caller's messageのみ使用（訓練時のデフォルトを破棄）
caller-supplied system message なし: モデル固有のデフォルトツール使用プロンプトを使用
```

ツール呼び出しの信頼性はデフォルトプロンプトの正確なバイト列に依存しているが、callerがsystem messageを提供した瞬間にこれが破棄される。さらに、デフォルトパスと明示的パスの末尾の空白（"\n\n" vs なし）の違いだけで出力が壊れる。

## 先行研究との比較

| 指標 | 未パッチ | パッチ後（CP込み） |
|------|---------|-----------------|
| MCPMark（Filesystem、easy） | 0/10（評価不可） | 3/10（30%） |
| BFCL シングルツール | 評価不可 | ほぼ完璧 |
| BFCL マルチツール | 評価不可 | 大多数が失敗 |
| 最大コンテキスト長（32 GiB） | — | ~11,231トークン |
| ナイーブプリフィルの最大コンテキスト長 | — | 4,096トークン |

コンテキスト長の比較：チャンク化プリフィルにより、32 GiB Apple Silicon上での最大コンテキスト長が4,096→11,231（2.7倍）に拡大。

## 実験結果の読み方

### LongBench-Pro評価（メモリvs速度トレードオフ）

| prompt_len | ナイーブPF最大BS | チャンクPF最大BS | 速度オーバーヘッド |
|------------|----------------|----------------|-----------------|
| 1,024 | 2 | 4 | +22.8% |
| 2,048 | 1 | 4 | +40.9% |
| 4,096 | 失敗 | 1 | — |
| 8,192 | 失敗 | 1 | — |
| 11,231 | 失敗 | 1 | — |

**重要な観察**:
- チャンク化プリフィルはバッチサイズが大きい（並列推論が多い）ほど速度オーバーヘッドが相対的に小さくなる（チャンク処理の固定コストが分散される）
- 4096以上のプロンプトでは、ナイーブプリフィルはApple Silicon 32GiBでバッチサイズ1でも失敗

### MCPMarkの30%という数字

Filesystem（easy）タスクで10問中3問成功（30%）。これは高く聞こえないかもしれないが、コンテキストを理解することが重要：

- 未パッチ版：評価自体が不可能（0%）
- パッチ後：3/10を達成——これはバグなく動作するモデルとしての「実際の性能」

失敗パターンの分析が興味深い：pattern_matchingタスクでモデルは正しいMCPツールを呼び出せたが、絶対パスを21回繰り返してタイムアウト。これはツール呼び出し能力よりも出力制御の問題を示唆している。

## アルゴリズムの重要部分の解説

### Looped Transformerのアテンションメモリを数式で理解

通常のself-attentionのメモリ計算：

```
Attention(Q, K, V) = softmax(QK^T / √d_k) V
```

各レイヤーでアテンションスコア行列QK^Tを計算する際、形状は(batch_size, heads, seq_len, seq_len)。つまり**1レイヤーあたりのメモリ = O(seq_len²)**。

Looped Transformerで2回パスを通すと：

```
Pass 1: Layer1...LayerL で O(L × seq_len²)
Pass 2: Layer1...LayerL で O(L × seq_len²) （同じ重みを再利用）
合計: O(2L × seq_len²)
```

通常のTransformerとパラメータ数が同じでも、**推論時ピークメモリは2倍**。

### チャンク化プリフィルのメモリ削減原理

チャンク化プリフィルではプロンプトをC個のチャンク（各chunk_size=256トークン）に分割：

```
チャンクi処理時のアテンション計算：
  - クエリ: chunk_size個のトークン
  - KV: それまでの全トークン（i×chunk_size個）
  - アテンション行列形状: (chunk_size × i×chunk_size)
  - = O(chunk_size × 全コンテキスト長)
```

これを全プロンプトへの比較：
```
通常: O(seq_len × seq_len) = O(seq_len²)
チャンク化: max O(chunk_size × seq_len) — seq_lenの係数をchunk_sizeに制限
```

**直感的なイメージ**: 本全体を一度に読んで質問に答えるのではなく（全ページの二乗コスト）、1ページずつ読みながら重要情報をノートに書き溜め（KVキャッシュ）、次のページを読む際はそのノートを参照する（線形コスト）。

### チャット・テンプレートのバイト列感度

```jinja2
{% if tools %}
  {% if messages[0]['role'] == 'system' %}
    {{ messages[0]['content'] }}\n\n  {# 末尾に\n\nが自動追加 #}
  {% else %}
    {{ DEFAULT_TOOL_PROMPT }}  {# \n\nなし、直後に# Toolsセクション #}
  {% endif %}
{% endif %}
```

callerがsystem messageを提供すると「\n\n」が追加される。モデルはデフォルトパス（\n\nなし）でファインチューニングされているため、この2文字の差が出力を破壊する。**モデルの推論はバイトレベルで精密**——これはどのプロダクションSLMでも起こりうる問題だ。

## 限界と課題

1. **30%の成功率**: easy tierで30%はプロダクションには不十分。複数ターンのコンテキスト蓄積による長期的なメモリ問題が主要な失敗原因

2. **マルチツール失敗**: BFCLシングルツールはほぼ完璧だが、マルチツールは大多数失敗。これはツール呼び出しのシーケンシャルな依存関係処理の限界を示す

3. **MPSメモリの永続的劣化**: 一度OOMが発生すると、プロセス再起動まで使用可能メモリが恒久的に減少する——PyTorch/MPSの根本的な問題

4. **チャンク化プリフィルの速度コスト**: 1024トークンで22.8%、2048トークンで40.9%の遅延増加。低遅延アプリケーションには許容できない場合がある

5. **汎化性の未検証**: パッチはM2 Maxで開発されており、他のApple Siliconバリアント（M4 Max、M-Ultraなど）での動作は確認されていない

## 今後の展望

**著者が示唆するFuture Work：**
- カーネルフュージョンによるチャンク化プリフィルのオーバーヘッド削減（逐次的なサブコールを少数の大きなGPU操作にまとめる）
- より広範なMCPMarkタスクでの評価

**この研究から派生しうる発展的な研究方向：**

1. **LTアーキテクチャ × 量子化**: Looped Transformerで重みを共有しながら量子化すると、1回目と2回目のパスで同じ量子化誤差が蓄積する。これが通常Transformerより悪化するか、あるいは誤差が自己打消しになるか、興味深い研究テーマだ

2. **統合メモリシステム向けSLM設計**: Apple Silicon、Snapdragon NPU、MediaTekのDimensityなど、統合メモリアーキテクチャでのSLM展開に最適化されたモデル設計の研究

3. **チャットテンプレートの形式仕様**: ツール呼び出しのロバスト性がバイト列精度に依存するという問題を解決するための、より堅牢なチャットテンプレート設計の標準化

4. **LT推論の動的ループ数**: プロンプトの複雑さに応じてループ数を1〜3に動的調整する適応型推論の可能性

5. **OOMからの回復メカニズム**: MPSバックエンドのメモリ永続劣化問題に対するランタイムレベルの解決策（PyTorchへのコントリビューション）

## エッジ・オンデバイスへの示唆

この研究はオンデバイスAI実務者にとって教科書的な価値がある：

**1. 「理論的性能」と「デバイス上動作」は別物**  
論文で報告された高いベンチマーク性能は、必ずしもそのモデルが実際のデバイスで動くことを意味しない。本研究では5つのバグ全てが修正されて初めて評価が可能になった。

**2. 統合メモリシステムは独特の制約を持つ**  
Apple SiliconはOS、GPU処理、モデル推論が同じメモリプールを共有する。CUDA環境とは異なるメモリ管理の挙動（ページアウトなし、OOM後の永続劣化）は、モデルアーキテクチャ選択に影響を与えるべき要因だ。

**3. チャンク化プリフィルは汎用的な技術**  
LT固有の問題だけでなく、長いシステムプロンプト（RAGドキュメント、ツール定義の羅列）を持つ任意のSLMでメモリを削減できる可能性がある。

**4. プロダクション展開での現実的性能**  
30%（easy tier）という数値は、現時点での3B級SLMがエージェンティックタスクで達成できる現実的な上限の目安を提供する。プロダクション投入前に類似のベンチマークを実施すべきだ。

**5. チャットテンプレートの品質管理**  
SLMのツール呼び出し信頼性がチャットテンプレートのバイト列精度に依存するという発見は、モデルリリース時のチェックリストに「多様なsystem messageでのツール呼び出しテスト」を加えるべきことを示唆している。
