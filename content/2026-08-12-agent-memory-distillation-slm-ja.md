Title: AMD: 階層的な教師メモリでSLMエージェントを強化する
Date: 2026-08-12
Category: AI/ML
Tags: SLM, AI, 論文解説
Summary: 大規模教師エージェントの成功軌跡から階層的メモリを蒸留し、4B〜8B規模の小型エージェントをGPT-5-mini並みの性能に引き上げる学習不要フレームワーク「AMD」の技術解説。

## なぜこの研究が重要か

ツール呼び出しを伴う複雑なエージェントタスク（APIオーケストレーション、マルチアプリ操作など）において、小型言語モデル（SLM）は致命的な欠点を抱えている。それは「成功軌跡の貧しさ」だ。

**根本的な問題**：SLMはそもそも成功体験が少ないため、従来のメモリベース学習が機能しない。

エージェント系の研究ではメモリ（過去の成功パターンを保持・再利用する仕組み）が重要な役割を果たすことが実証されている。GPT-4やGemini 2.5のような大規模モデルなら自力で多くのタスクを解けるので、成功軌跡が豊富に蓄積される。しかしQwen3-4BやLlama3.1-8Bのような小型モデルは、ゼロショットでの成功率が著しく低く、ほとんどの記憶が「失敗した体験」で占められてしまう。失敗から学べることには限界があり、構造化された成功パターンがなければメモリは機能しない。

さらに深刻なのは、**ナイーブな教師メモリ転送も機能しない**という点だ。大きな教師モデルが「まずログインしてからプレイリストを開始する」と言っても、小型学生モデルはその「ログイン」の実行手順自体を知らないことがある。教師の高レベルな指示を実行するための下位能力が学生には欠けているのだ。

この問題は従来の知識蒸留研究で観察されている「教師・学生間の能力ギャップ」問題のエージェント版であり、解決するには**粒度を階層的に構造化した知識転送**が必要となる。

## 技術的なアプローチ

AMD（Agent Memory Distillation）は、大規模教師エージェントの成功軌跡から3種類の階層的メモリを構築し、それを小型学生エージェントに転送する学習不要フレームワークだ。

### 3つの階層的メモリ

**① Workflow Memory（タスクレベル）**

教師の成功軌跡全体から、タスク完了のための高レベル戦略を言語化したもの。使用するアプリ・ツール、主要な前提条件、タスク完了のための判断ルール、避けるべき失敗パターンが含まれる。

重要な点として、動的な実行時の値（ID、メールアドレス、ファイルパスなど）は `<ID>`, `<EMAIL>`, `<FILE_PATH>` のようなプレースホルダーに置き換えられる。これにより、具体的な値が異なる将来のタスクにも適用可能な汎用的な知識として保存される。

数式で表すと、各成功軌跡 $\tau_i^T$ から insight $\text{ins}_i$ とクエリ $q_i$ のペア $m_i^{wf} = (q_i, \text{ins}_i)$ が生成され、密ベクトルとして埋め込まれてリトリーバルに使用される。

**② Subtask Memory（サブタスクレベル）**

Workflow と Function の中間に位置する「具体的な行動例」。成功軌跡を意味的にまとまりのある単位（例：「サービスへの認証」「一連の関連APIコールの実行」）に分割し、各単位の実際のツール呼び出しと観測結果を保存する。

各サブタスクセグメント $e_{i,k}$ はラベル $\ell_{i,k}$、説明 $d_{i,k}$、実行例 $e_{i,k}$ の三つ組 $m_{i,k}^{st} = (\ell_{i,k}, d_{i,k}, e_{i,k})$ として保存される。

**③ Function Memory（関数レベル）**

個々のツール呼び出しの慣例を捉えたもの。各関数呼び出し $f_{i,j}$ に対して、具体的な実行例 $E_{i,j}$（呼び出しコンテキスト、引数、返値）とAPI仕様 $\text{doc}(f_{i,j})$ をまとめた $m_{i,j}^{fn} = (f_{i,j}, E_{i,j}, \text{doc}(f_{i,j}))$ として保存される。

### メモリの注入方法

メモリ注入には**先行注入**と**後発注入**の2方式がある。

**先行注入（Proactive Injection）**：タスク開始前にWorkflow MemoryとSubtask Memoryをシステムプロンプトに埋め込む。学生エージェントはタスク実行前から高レベルな計画と具体的な行動例を知った状態でスタートできる。

- Workflow: タスク指示をクエリとして、コサイン類似度でトップ1のWorkflow Memoryエントリを取得
- Subtask: まず学生がタスクをサブタスクに分解し（最大6個）、各サブタスクラベルをクエリとしてSubtask Memoryを検索

**後発注入（Reactive Injection）**：ツール呼び出しがエラーを返した時のみFunction Memoryを動的に取得する。失敗した関数名でFunction Memoryを検索し、該当するサンプルをエラーメッセージに付加する。これにより、成功時のコンテキスト肥大化を防ぎつつ、失敗時には的確な修正ヒントを提供できる。

## 先行研究との比較

| 手法 | メモリ粒度 | 学習必要 | クロスモデル転送 |
|------|-----------|---------|---------------|
| ReasoningBank | タスクレベル（フラット） | 不要 | △ |
| MemP | 階層的（同モデル前提） | 不要 | × |
| SASM | サブタスクレベル | 不要 | △ |
| **AMD** | **3階層（WF+ST+FN）** | **不要** | **○** |

既存の手法が「同一モデルの自己発展」を想定しているのに対し、AMDは「大型教師→小型学生」という非対称な知識転送を明示的に設計した初の研究だ。

## 実験結果の読み方

3つのベンチマーク、4つの学生モデル（Qwen3-4B, Qwen3-8B, Gemma4-E4B, Llama3.1-8B）でAMDを評価した。

**AppWorld（168タスク）**：最も劇的な改善。
- Qwen3-4B: 14.88% → 49.40%（**+34.52%p**）
- Gemma4-E4B: ? → 54.17%（教師のGPT-5-mini: 50.00%を**超過**）
- Qwen3-8B: ? → 51.79%（同じく教師を超過）

AppWorldは複数のアプリ（メール、決済、メッセージング等）を跨ぐ長期タスクで、教師を超えるという結果は衝撃的だ。学生が単に教師の軌跡を模倣するのではなく、各モデルの帰納的バイアスに合わせて意思決定パターンを再インスタンス化した結果とも解釈できる。

**BFCL V3（200タスク）**：
- 平均+11.2%p。3つの学生モデルが教師を超過（教師平均: 38.39%、Qwen3-8B: 40.96%）

**ToolSandbox（129シナリオ）**：
- 平均+3.4%p。長期会話での実世界ツール依存タスクであり、最も難易度が高い

**比較手法（ReasoningBank, MemP, SASM）はAppWorldでマイナスになる**ケースもあった（ReasoningBankでQwen3-4B: 14.88% → 10.71%）。これは構造化されていない教師メモリがノイズとなって学生の推論を妨げることを示す。

**インタラクション効率**：AMDはタスク完了に要するターン数も削減する。AppWorldでQwen3-4Bのゼロショット平均ターン数は23.8だったのに対し、AMD後は14.9に減少（教師は10.1）。

## アルゴリズムの重要部分の解説

AMDの核心は**メモリ生成**と**メモリ注入**の2フェーズから成る。

### フェーズ1: 階層的メモリ生成

$$\mathcal{M} = \mathcal{M}^{wf} \cup \mathcal{M}^{st} \cup \mathcal{M}^{fn}$$

教師の成功軌跡集合 $\mathcal{D}^T_+$ からこの3種のメモリを生成する。ポイントは「成功した軌跡だけ」から生成することだ。失敗軌跡は含まない。これにより高品質な知識が保証される。

各メモリタイプが解決する問題を整理すると：
- **Workflow** → 「何を達成すべきか・どの順番で行動すべきか」
- **Subtask** → 「各ステージでどのように行動したか（具体例付き）」
- **Function** → 「特定ツールの正しい使い方（引数・戻り値・エラー対処）」

この3層は人間のスキル習得と対応する。まず全体の流れ（Workflow）を把握し、各フェーズの手順（Subtask）を学び、具体的なツール操作（Function）を身につけるという構造だ。

### フェーズ2: 推論時の注入

$$R(\pi^S(s; \mathcal{M})) \text{ を最大化}$$

これがAMDの目標関数だ。学習によるパラメータ更新は行わず、メモリを介した文脈注入のみで学生エージェントの報酬を最大化する。

具体的なアルゴリズムの流れ：

```
タスク開始時:
  1. タスク指示 → Workflow Memory検索（コサイン類似度）
  2. 学生がサブタスクを分解 → 各サブタスク → Subtask Memory検索
  3. 取得したメモリをシステムプロンプトに注入

実行中:
  4. ツール呼び出しがエラー → 関数名 → Function Memory検索
  5. 取得した使用例をエラーメッセージに付加
```

**「なぜコサイン類似度で検索するのか」**：メモリは密なベクトルとして事前にエンコードされている（OpenAIのtext-embedding-3-smallを使用）。クエリ（タスク指示やサブタスク説明）もベクトル化し、コサイン類似度が高いものを取得する。これにより「意味的に類似した過去のタスク」から知識を引き出せる。最小類似度閾値以下のエントリは除外される。

**「k=1が最適である理由」**：実験では取得件数kを変化させた結果、k=1が最適だった。k>1になると、小型モデルは複数のメモリから重要な情報を選別・統合する能力が不足しているため、かえってノイズとなる。これはSLMの文脈内学習能力の限界を示す重要な発見だ。

## 限界と課題

論文が認めている制約：

1. **計算コスト（メモリ生成側）**：教師エージェント（GPT-5-mini）によるタスク実行と高品質なメモリ生成にはAPIコストがかかる。これは学習不要である恩恵があるが、初期投資として必要。

2. **1.7Bモデルでは限界**：Qwen3-1.7Bでの検証では、AMD後も絶対精度は21.43%に留まった。モデル容量が小さすぎると、注入されたメモリを理解・適用する能力自体が不足する。

3. **教師・学生互換性の問題**：4B学生では、より強い教師（GPT-5.5、DeepSeek V4 Pro）よりも中程度の教師（GPT-5-mini）からの転送が良好だった。これは「能力ギャップが大きすぎると、教師の知識が学生には難解すぎる」という知識蒸留の古典的問題のエージェント版だ。

4. **評価対象ベンチマークの範囲**：実験は3つのツール使用ベンチマークに限定。プログラミング、数学推論、視覚理解など他のドメインへの汎化は未検証。

## 今後の展望

**著者が示唆する方向**：

- AMDで得たメモリを使った後から学生モデルをファインチューニングする「メモリ蒸留 + 学習」の組み合わせ
- メモリ生成のコストを下げるためのメモリ圧縮・要約技術の研究
- より大規模なタスクセットでの検証

**さらに発展が見込まれる方向**：

**継続的メモリ更新**：現状のAMDは静的なメモリバンクを使用しているが、学生が新しいタスクを解いていくにつれてメモリを動的に更新・精錬する仕組みが有効なはずだ。学生自身が一部のタスクで成功し、その軌跡をメモリバンクに追加することで、教師依存度を徐々に下げていける。

**メモリ品質の選別**：現状は成功軌跡をすべてメモリ化するが、多様性（タスクのカバレッジ）や難易度（学生にとって有益な難しさ）を考慮した選別が性能向上につながる可能性がある。

**マルチ教師アンサンブル**：実験では単一の教師を使用したが、複数の教師モデルからメモリを収集し、アンサンブルすることで頑健性が向上するだろう。

## エッジ・オンデバイスへの示唆

AMDの最も重要な実用上の意義は、**コストのかかる推論を実行時ではなく事前準備時に行う**という設計思想だ。

現実のエッジ・オンデバイス展開では：

- **メモリ構築フェーズ**（教師による軌跡実行）：クラウドサーバー上で一度だけ実行
- **推論フェーズ**（学生エージェントの実行）：オンデバイスで継続的に実行

この分離により、デバイス上では4B〜8B規模の小型モデルだけが動作し、大型モデルへのAPI呼び出しは不要になる。特にAPIアクセスが困難な環境（エッジIoT、航空機内、低帯域地域）での自律エージェント展開に有効だ。

ただし、現状のメモリサイズ（各タスクのWorkflow、複数のSubtask、Function記録）は相当な量になる可能性があり、メモリ制約の厳しいデバイスでのインデックス管理が課題となる。量子化やメモリ圧縮との組み合わせが今後の研究テーマになるだろう。
